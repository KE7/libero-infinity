# G7 Human Semantic Review Rubric — Libero-Infinity

**Purpose.** This document is the reviewer's manual for Gate G7 of the Libero-Infinity
publication validation. G0–G6 establish *mechanical* validity (parse, compile, sample,
instantiate, simulate). G7 establishes *semantic* validity: for every sampled `(task,
axis_subset, seed)` triple, a human verifies that the generated Scenic program still
encodes the BDDL task in a way a fair benchmark would accept.

A *review packet* is a self-contained directory generated by
`libero_infinity.validation.review_packet` containing the original BDDL, the parsed
task graph, the generated Scenic program, a diff against the no-axes baseline,
sampled axis parameters, a rendered scene, and an empty checklist. Reviewers grade
each packet by filling in `checklist.yaml`.

---

## 1. How to read a packet

A packet directory contains:

| File | What it is | What to look at |
|---|---|---|
| `bddl/original.bddl` | The canonical BDDL task. | The `:goal` block — that defines the success condition the policy must achieve. |
| `task_language.md` | The natural-language instruction. | Confirm the rendered scene plausibly matches this description. |
| `task_graph.md` | Parsed objects, fixtures, regions, init predicates, goal predicates. | Cross-check that no required object/fixture is missing from the Scenic program. |
| `scenic/generated.scenic` | The Scenic program emitted for `(task, axis_subset)`. | This is the artifact under review. |
| `scenic/baseline_diff.md` | Unified diff vs the `none`-axis baseline (same task, no perturbations). | Quickly localizes what each axis added. |
| `axis_params.json` | The concrete values sampled per axis (e.g. `position.delta_xyz`, `object.variant`). | Verify each perturbation stayed inside its declared envelope. |
| `compiler_diagnostics.txt` | Compiler warnings + diagnostics. | Treat any warning as a Severity-1 cue unless explained. |
| `rendered/scene.png` | A single sampled scene rendered to PNG. | Spot-check geometry, occlusion, fixture state, robot pose. |
| `checklist.yaml` | The grading sheet. | Fill in. |

Read in this order: `task_language.md` → `task_graph.md` → `bddl/original.bddl` (goal
block only) → `rendered/scene.png` → `scenic/baseline_diff.md` → `axis_params.json` →
finally `scenic/generated.scenic` to resolve ambiguity.

A trained reviewer should spend ≈3–7 min on a typical packet, 10–15 min on a
LIBERO-10 long-horizon task or a `combined`/`full` subset.

## 2. Severity rubric

Each checklist question receives a single integer severity from this scale:

| Severity | Label | Meaning | Action |
|---|---|---|---|
| **0** | No issue | The artifact is correct. | None. |
| **1** | Cosmetic | Stylistic noise, redundant comments, unused declarations — does not change semantics or feasibility. | Note in margin; no fix required. |
| **2** | Minor | A real but bounded deviation that does not break the task: e.g. a distractor slightly inside an aesthetic margin, an extra `require` that is satisfied by 99 % of samples. **Will be footnoted in the paper.** | Note in `notes`; aggregator includes in caveats table. |
| **3** | Significant | The artifact would unfairly penalize or reward some policies: e.g. an object substitution that makes the goal trivially solved, a camera that occludes the manipulated object on >5 % of samples, a region the goal can no longer be satisfied in. **Requires narrowing the axis envelope or a targeted code fix and a re-run of the affected packets.** | Aggregator flags as fix-and-rerun. |
| **4** | Critical | The artifact breaks the BDDL goal semantics outright: e.g. a fixture that the goal references is removed, a required predicate is unreachable in every sample, the rendered scene contradicts the task language. **Task or axis must be removed, or the compiler must be repaired and the entire layer regenerated.** | Aggregator blocks publication-grade claim. |

A packet's overall severity is the **maximum** of its per-question severities.

## 3. Checklist questions

The packet's `checklist.yaml` has eleven entries. Each entry takes:

```yaml
- id: q1_goal_semantics
  severity: 0          # 0–4
  reviewer: <handle>
  notes: ""            # free text; required when severity >= 2
```

The questions, verbatim, with elaboration and pass / minor-fail / critical-fail
examples.

### Q1. Does the Scenic program preserve the BDDL goal semantics?

Every `:goal` predicate in `bddl/original.bddl` must still be *achievable* in the
Scenic-sampled scene by a competent policy executing the natural-language
instruction.

- **Pass (0):** Each goal predicate refers to objects/fixtures/regions that exist
  in the Scenic program with consistent identities; clearances allow the goal
  pose; nothing in the perturbation forces the goal false at termination.
- **Minor-fail (2):** The goal is still achievable on essentially every sample,
  but on a small minority (<5 %) the perturbed camera or distractor placement
  makes the goal *harder to verify* without changing the underlying success
  condition.
- **Critical-fail (4):** A fixture referenced in the goal predicate has been
  removed (e.g. `On(bowl, plate)` but no `plate` instance in the Scenic
  program), or the perturbed pose places the target outside the only
  satisfying region.

### Q2. Are all BDDL-declared objects, fixtures, and regions present in the Scenic program?

The parsed `task_graph.md` lists every entity the BDDL declares; cross-check that
each appears in `scenic/generated.scenic` (possibly under an object-axis
substitution, see Q5).

- **Pass (0):** 1-to-1 correspondence (modulo intentional object-axis
  substitution).
- **Minor-fail (2):** A redundant declaration is present but unused.
- **Critical-fail (4):** A BDDL-declared object/fixture is missing or has a
  type that the substitution table does not permit.

### Q3. Are the init predicates respected?

`:init` predicates (e.g. `On(bowl, table)`, `In(soup, basket)`) constrain the
starting pose. The Scenic program must impose equivalent constraints (`require`
blocks, regions, supports) so that **at sampling time** every drawn scene
satisfies the BDDL init.

- **Pass (0):** Every `:init` predicate maps to an explicit Scenic `require` or
  a region-based placement that implies it.
- **Minor-fail (2):** A predicate is implied by geometry but not stated; the
  invariant holds in practice but is implicit.
- **Critical-fail (4):** A predicate is not enforced and a non-trivial fraction
  of samples violate it.

### Q4. Are the perturbations within their declared envelopes?

`axis_params.json` lists the concrete sampled value per active axis. Cross-check
against the axis's documented envelope (see `docs/architecture.md` and per-axis
plan docs).

- **Pass (0):** Every value is inside its envelope.
- **Minor-fail (2):** A value sits at the very edge of its envelope on a corner
  case (e.g. lighting RGB clamped to 0.99); not in practice problematic.
- **Critical-fail (4):** A value is out of range — e.g. camera tilt sampled
  outside ±15° — and the policy's input distribution is no longer fair.

### Q5. If the object axis is active, do substituted objects preserve the task's affordances?

E.g. substituting a "bowl" with a "mug" must still allow the `On(?, plate)`
goal; substituting a graspable with a non-graspable breaks the task.

- **Pass (0):** Substituted object is a valid member of the equivalence class
  (same affordance, similar size).
- **Minor-fail (2):** The substituted object is in-class but unusually small /
  large; the goal is still achievable but pose tolerance must increase.
- **Critical-fail (4):** Substituted object lacks the required affordance
  (e.g. cannot be picked, cannot contain).

### Q6. If the distractor axis is active, do distractors avoid blocking the goal?

Distractors must not collide with the manipulated object's grasp approach, must
not occlude the goal fixture, and must not be themselves placed *in* the goal
region.

- **Pass (0):** Distractors live in workspace cells disjoint from the goal
  region and grasp approach.
- **Minor-fail (2):** A distractor sits close to the grasp approach on a small
  fraction of samples but reachable trajectories still exist.
- **Critical-fail (4):** A distractor is sampled *inside* the goal region or
  blocks the only feasible approach.

### Q7. If the articulation axis is active, are joint sample ranges consistent with the goal?

E.g. for `Open(drawer)`, the drawer must be sampled *closed* at init; for
`Close(drawer)`, sampled *open*; for tasks indifferent to drawer state, either
is fine but the sampled state must be physically valid.

- **Pass (0):** Joint values consistent with init/goal and within mechanism
  limits.
- **Minor-fail (2):** Joint sampled at exactly the goal value (so the goal is
  trivially solved on init); only OK if the BDDL semantics tolerate this.
- **Critical-fail (4):** Joint sampled at a value the mechanism cannot
  physically reach, or that contradicts the goal predicate at init.

### Q8. Is the natural-language instruction still faithful to the rendered scene?

Compare `task_language.md` against `rendered/scene.png`.

- **Pass (0):** A naive reader could point to each noun in the rendered image.
- **Minor-fail (2):** A named object is partially occluded but identifiable.
- **Critical-fail (4):** A named object is absent or replaced by an
  unrecognizable substitute (e.g. instruction says "red mug" but only a white
  bowl is visible).

### Q9. Are there compiler diagnostics or warnings that hint at a semantic issue?

Read `compiler_diagnostics.txt`. Warnings about dropped axes, collapsed variant
pools, or unsatisfied `require` clauses are leading indicators of Q1–Q3
problems.

- **Pass (0):** No diagnostics, or only informational ones.
- **Minor-fail (2):** A diagnostic of the form "axis dropped: no valid
  variants" with the corresponding axis correctly absent from sampling.
- **Critical-fail (4):** A diagnostic indicates a planner crash, a silently
  swallowed exception, or a goal-fixture variant pool collapsed to zero.

### Q10. Is the rendered scene physically plausible (no float-throughs, intersections, fallen-over fixtures)?

A quick eyeball of `rendered/scene.png`.

- **Pass (0):** Everything rests on a support; nothing intersects.
- **Minor-fail (2):** Minor visual artifact (texture seam, small Z-fight) that
  does not affect physics.
- **Critical-fail (4):** An object floats / intersects / is below table /
  fixture has tipped — physical infeasibility.

### Q11. Does the baseline diff isolate the perturbation cleanly, or does it leak unrelated changes?

Read `scenic/baseline_diff.md`. Every line of diff should be attributable to an
*active* axis. Lines that touch un-requested axes signal cross-axis leakage.

- **Pass (0):** All diff hunks are attributable to the active axes listed in
  `axis_subset`.
- **Minor-fail (2):** A cosmetic change (whitespace, header comment date)
  unrelated to axes.
- **Critical-fail (4):** A perturbation appears that was not requested (e.g.
  camera tilt sampled in a `position`-only packet).

## 4. Adjudication protocol

Each packet is reviewed by **at least two independent reviewers**. After both
have submitted:

1. The aggregator (`review_aggregate.py`) computes, per question, the
   per-reviewer severities and their max-disagreement.
2. **Agreement (Δ severity ≤ 1):** the packet's severity for that question is
   the **max** of the two scores. No adjudication needed.
3. **Disagreement (Δ severity ≥ 2):** a third reviewer (the *adjudicator*) is
   assigned. The adjudicator:
   - reviews the packet independently, *without* seeing the other reviewers'
     scores;
   - then sees the other reviewers' notes and reconciles;
   - records the final severity and a free-text adjudication note.
4. **Adjudicator's score wins** on disagreed questions; on questions where
   reviewers agreed, the agreed severity stands.
5. All three severities are retained in `checklist.yaml` under `severity`,
   `reviewer2_severity`, `adjudicator_severity` so kappa can be recomputed.

If the adjudicator and the original reviewers form a 2-vs-1 split where the
adjudicator's score is the outlier, the chief reviewer escalates to a panel
discussion at the weekly review meeting; the panel's consensus severity is
recorded with `adjudicator_severity` and `adjudicator: panel-YYYY-MM-DD`.

## 5. Inter-rater agreement reporting

The aggregator produces, for each layer of the sampling design:

- **Per-question Cohen's κ** (two-rater, ordinal) on the raw 0–4 severity
  scale, computed before adjudication.
- **Per-question Krippendorff's α** (any number of raters, ordinal,
  missing-data-tolerant) for layers where some packets have ≥3 reviewers.
- **Aggregated κ̄ and ᾱ across questions**, equal-weighted.
- **Cell counts** for each (severity, severity) pair, so readers can recompute.

Target thresholds (publication-grade):

| Statistic | Acceptable | Concerning |
|---|---|---|
| Mean per-question κ | ≥ 0.65 | < 0.50 |
| Min per-question κ | ≥ 0.50 | < 0.30 |
| Mean α | ≥ 0.70 | < 0.55 |

If a question falls below the "concerning" threshold, the question is flagged
in the publication caveats: either the question wording is rewritten and the
review repeats on a sub-sample, or the question is dropped from the
publication-grade claim with disclosure.

## 6. Conflict-of-interest disclosure

Each reviewer signs a one-page CoI form before being shown packets. The form
requires disclosure of:

1. **Authorship overlap.** Whether the reviewer is an author or
   acknowledged contributor of the libero-infinity codebase, the LIBERO
   benchmark, or any Scenic-related codebase under review.
2. **Funding / employer overlap** with any author of the present paper in
   the past 24 months.
3. **Prior exposure** to the specific packets being reviewed.
4. **Code-authorship overlap** with any commit referenced in the packet's
   `axis_params.json` provenance fields.

Reviewers with any disclosure are still eligible to review packets but are
assigned packets whose authoring code path they did **not** write, where
possible. Disclosure status is recorded in `checklist.yaml` under
`coi_disclosed: true|false` and the disclosure form is filed alongside the
packet tree. The aggregator emits a per-reviewer disclosure summary in the
final report.

## 7. Reviewer quick reference

1. Read the natural-language task; sanity-check the render.
2. Walk `task_graph.md` → check every object/fixture appears in
   `scenic/generated.scenic`.
3. Open `axis_params.json`; for each active axis, verify the value is in
   envelope.
4. Read `scenic/baseline_diff.md`; verify diff is fully axis-attributable.
5. Fill in `checklist.yaml`; for any severity ≥ 2, write a `notes` paragraph
   citing the specific file and line.
6. Submit.

If you find yourself uncertain between two adjacent severities (e.g. 1 vs 2),
**pick the higher**: false-positive flags are easier to dismiss in
adjudication than false negatives.
